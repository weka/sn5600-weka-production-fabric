# Lossless RoCE addition — Cumulus Linux 5.11.5

This is a switch-side RoCEv2 baseline for the existing eight SN5600 switches, after the /31 migration in this bundle. It is not a complete host/server deployment. The scripts do not configure NICs, host routes, access VLANs, host-facing breakouts or server subnet advertisements.

## Policy

Use NVIDIA's standard lossless RoCE profile, with automatic PFC buffer/threshold calculation, PFC on priority 3, ECN, RoCE traffic class 3, and CNP traffic class 6. The documented default classification maps DSCP 26 to switch priority 3 and DSCP 48 to switch priority 6. CNP has strict-priority scheduling. These are generated by NVUE; this bundle does not copy ASIC QoS files or hard-code byte thresholds.

The actual configuration delta is identical on all eight switches:

```bash
nv set qos roce
nv set qos roce mode lossless
```

The scripts inspect the pending diff before applying and save after applying. The standard profile is global to the switch's data ports, including host-facing and reserved ports. It does not change their link administrative states. No connection or command targets 172.31.17.3.

Native 800G links continue to use ECMP. Cumulus 5.11 documents adaptive routing as unsupported on Spectrum-4 800G links. The custom adaptive-routing profile/snippet from the supplied references is not included. The references' 353000-byte port buffer, 65000-byte XOFF/XON values and spine-only 90/10 pool allocation are not imported. The example breakouts, tenant VRFs, EVPN, users, credentials and management settings are also not part of this delta.

The reference leaf uses `state enabled` syntax. This package uses the documented Cumulus 5.11 `nv set qos roce` form and explicitly selects lossless mode.

## Before enabling

1. Complete the /31 addressing/BGP stages for all four spine groups. Existing /31 migration backups must remain on each switch.
2. Run `bash fabric.sh validate`. Resolve new routing failures. Existing missing-link warnings are not repaired by RoCE.
3. Schedule a maintenance window. Global QoS buffer changes can cause momentary packet loss. Enabling the switches sequentially is not a hitless guarantee.
4. Run configuration work from one operator session at a time. The scripts stop if any pending NVUE diff, custom QoS, per-interface QoS, incompatible native-800G adaptive routing or NVUE file snippets are found. Reconcile an unexpected existing policy rather than deleting it to bypass the check.

The supplied reference files are policy examples, not proof of a supported or tuned 800G configuration for this fabric.

## Run from the Mac

After extracting the new ZIP and copying with `bash fabric.sh copy`:

```bash
bash fabric.sh roce-check
bash fabric.sh roce-apply
bash fabric.sh roce-validate
```

`roce-check` is read-only. `roce-apply` checks every selected switch first, then applies to one switch at a time in this order: spine-01 (.5), spine-02 (.18), spine-03 (.20), spine-04 (.22), leaf-01 (.19), leaf-02 (.21), leaf-03 (.23), leaf-04 (.24). It validates each switch before moving to the next. If a step fails, stop, review its output and pending diff. Earlier switches can already have RoCE applied.

For individual control, use a name from the eight-switch plan:

```bash
bash fabric.sh roce-apply spine-01
bash fabric.sh roce-validate spine-01
```

An already configured standard lossless profile is verified without another apply. A stage-only candidate must be applied manually or detached before retrying; rerunning with `--apply` does not bypass pending-change protection.

The stage command backs up the original applied configuration and RoCE state under `~/sn5600-roce-state/<hostname>/`. Keep that directory. The existing numbered-BGP baseline is separate and remains unchanged.

## Verification and limits

The automated check verifies lossless mode, ECN including traffic class 3, PFC priority 3 with receive/transmit enabled, and DSCP trust globally and on all 32 fabric interfaces. It also runs the existing numbered-BGP, 800G/MTU and loopback checks and checks for BGP sessions lost since the RoCE baseline. Detailed per-port QoS output is saved as `~/sn5600-roce-state/<hostname>/latest-validation.txt`.

If NVUE returns an unfamiliar output format, the check fails rather than treating missing fields as success. Read the saved output before assuming the hardware configuration is wrong.

Check one connected fabric port at both ends. On a leaf use, for example:

```bash
nv show qos roce
nv show interface swp33 qos roce status
nv show interface swp33 qos roce counters
```

On a spine use the matching `swp1` (Leaf-01), `swp9` (Leaf-02), `swp17` (Leaf-03) or `swp25` (Leaf-04). Read the classification/scheduling tables: RoCE DSCP 26/SP3/TC3, CNP DSCP 48/SP6/TC6, CNP strict priority. Also inspect the actual generated buffer values. Buffer headroom depends on speed and cable delay; confirm the installed fiber length before custom tuning. The known DACs are 3 m; the fiber length has not been supplied.

Before and during representative RDMA load, compare counters at both ends for RoCE traffic, ECN marking, PFC pause activity, buffer discards, FEC errors and link flaps. Zero ECN/PFC counters while idle do not indicate a problem. A switch configuration pass or loopback ping does not prove sustained losslessness, throughput, or correct host-side congestion control. Current missing links remain DEGRADED even if QoS configuration passes.

## Host work still required

- Confirm NIC model, firmware/driver and supported RoCEv2/congestion-control configuration.
- Assign server-facing leaf ports, speeds/breakouts, server IP subnets/VLANs and routing advertisements.
- Match host traffic markings to RoCE DSCP 26 and CNP DSCP 48, PFC priority 3, and ECN/CNP handling. These are DSCP values, not complete IP ToS bytes.
- Match host/link MTU and verify with host-to-host RDMA traffic. Fabric port MTU remains 9216; test packet sizing is separate.

The current /31 fabric advertises switch loopbacks only. It does not yet provide routing between unconfigured server networks. Host-specific commands need the actual NICs and server port/address plan.

## Roll back this addition

On the Mac, restore a named switch's saved pre-RoCE state:

```bash
bash fabric.sh roce-rollback leaf-01
```

Or stage on that switch:

```bash
cd /home/cumulus/SN5600_Numbered31
bash leaf-01.sh roce-rollback
nv config diff
nv config apply && nv config save
```

This restores only the saved `qos roce` state and retains numbered BGP and addresses. It stops if later custom QoS makes the rollback ambiguous. If RoCE was already enabled before using this package, rollback can legitimately leave it enabled. If you enabled RoCE manually without the helper, it has no prior baseline to restore. Rollback is not automatic; reverting QoS can also interrupt traffic. After rollback, run the normal fabric validation and inspect `nv show qos roce` against the saved original configuration.
